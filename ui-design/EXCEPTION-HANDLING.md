# Exception handling · iteration 152

Knowledge → Exception handling provides a local, explicit follow-up loop for three observed K-02 conditions: missing/unreceived or historical-guide-linked brief, declined facilitator allocation, and failed simulated session. Organization, Attention, workshop and K-02 pages link to the loop. My Work shows only the next responsible actor's open exception responsibilities, separately from authored assignment counts.

## Operate the loop

1. Owner opens a ticket against an observed condition; no automatic ticket or assignment is created.
2. Owner offers handling to Leo or Maya. The named recipient accepts or declines; a decline returns allocation to the owner.
3. Resolve the underlying issue through its own operational screen. The accepted handler then submits a separate response with rationale and the exact current remedy attached.
4. Owner independently reviews the response, requests more work or closes. Changed remedy evidence blocks closure until a fresh response. Owner can cancel an open ticket or explicitly reopen a closed ticket; reopening requires a new offer and acceptance.

The missing-brief remedy is a received latest brief with current guide input. A declined-allocation remedy requires accepted facilitation in a later workshop cycle. A failed-session remedy requires successful simulated execution in a later cycle. None of these establishes learning outcomes; workshop criterion review and organization goal evidence remain separate.

This is a bounded local prototype for Knowledge/K-02. Actor selectors are demo controls, not authentication. There is no server assignment, escalation timer, notification, production retry or organization-wide exception policy. Closing a ticket does not change the underlying brief, workshop, authority, assignment or goal records. Use separate tickets for other observed incidents; duplicate open tickets for the same exact incident snapshot are blocked.
