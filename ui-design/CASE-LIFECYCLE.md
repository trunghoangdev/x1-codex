# Workshop-brief coordination case lifecycle

Iteration 145 makes `current-workshop-brief` operational as a bounded local exercise. Open Knowledge → Cases → Obtain the current workshop brief. The publication-policy case retains its authored read-only definition.

## Responsibilities and decisions

Leo separately accepts the authored follow-up nomination before updating work or proposing resolution. Updates record what has been checked, what remains and why. Maya is the explicitly named local case-resolution reviewer: she can approve the exact proposal or request further work. Neither role grants publication authority or allocates workshop execution. The acting-person selector is a simulation control, not authentication.

A proposal requires the latest delivered brief, its exact receipt and, for a guide-linked brief, the current applicable K-01 input. Evidence freezes the dependency, provider/receiver assignment identities, brief content/version and receipt. Maya must inspect audience/schedule content against the authored closure requirements; delivery and receipt alone never close the case. A proposal is not an approval, and closing the case does not establish workshop success.

Leo or Maya can explicitly reopen an approved case. If the proposed/approved source changes or becomes unusable, current status says reopening is required. Historical approval remains; new proposals wait for reopening and current received input. Changed guide content or applicability can make a brief historical without rewriting it. Request further work returns the case to Leo; another proposal and independent review are required.

## Shared and personal views

The case directory and Leo's follow-up card derive current status and next action from retained local events. A separate case-progress panel connects Organization, K-02, its workflow and relevant personal entrances. Maya sees pending case review separately from her authored assignment counts. Active local case needs appear in shared attention; resolved cases contribute no pending case signal. Existing authored responsibility and outcome gaps remain independently visible.

Original case requirements and source links remain in an authored-context disclosure. The local panel shows latest recorded rationale, a readable brief, exact evidence and retained history. All mutations require a review/confirmation step; cancellation or a changed preview leaves state unchanged.

## Recovery and history

`KnowledgeWorkspace.caseEvents` is an optional root slice, separate from brief delivery and contribution state. Whole-workspace checkpoint v11 replays transitions, actors, proposal links, exact evidence, chronological context and retained brief/handoff lineage. Each event freezes validated brief/contribution context, so historical decisions remain inspectable after source revisions. Older checkpoints remain readable; restoring one without case events replaces this slice with an empty history.

Contribution-only replacement retains case history and briefs. Any resulting linked-source mismatch makes proposed/approved resolution historical. Checkpoint preview identifies changed case history; restore/import is explicit and does not automatically save. Local case events appear in the retained Knowledge timeline under Coordination case, with actor, source and proposal references.

The exercise supports at most forty case records. The existing 4 MB checkpoint/file limit and browser storage limits still apply. This is not durable shared state, a general case engine or verified production authority.
